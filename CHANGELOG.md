Changelog
=========

## 4.2.0 (2026-08-31)

### Changed

- **Fallback command serialization is now scoped to a declared `if_not.group` instead of the whole process**: 4.1.0 put every `if_not.cmd` behind a single process-wide lock so that concurrent failures could not fire a restart storm or interleave the output of a shared script. That scope was too broad. Contention arises exactly when it is least affordable — several services failing on the same tick, most often because a shared dependency went down — and under the global lock those services recovered strictly one after another. A service at position *k* in the queue waited *(k-1) × T* for its turn, and was skipped once that exceeded its `if_not.timeout` (300s by default), so roughly `1 + 300/T` services could be repaired per scan. With a fast restart the cost is invisible; with a slow one — `systemctl restart` on a database — a single service holding the lock for minutes starved every unrelated service behind it, and epazote's own protection became the reason they stayed down. Serialization is now opt-in per conflict: services sharing an `if_not.group` run one at a time, and everything else runs concurrently as it did before 4.1.0. The queueing semantics are unchanged within a group — the wait is still bounded by `timeout`, a command still queued when that runs out is still skipped and logged for the next failed check to retry, the two phases are still budgeted separately so a command that starts is never killed part-way through, and the `stop` refund for an attempt in which nothing ran still applies. Since an ungrouped command never queues, it always runs and so always spends its `stop` attempt; the refund path is now reachable only inside a group.

  **This is a behaviour change for anyone running 4.1.0** — the serialization it introduced was implicit, and switching the default back means it is now silently absent unless declared. If several services share a fallback script, give them a `group`. If their restarts contend for the same resource, give them a `group`. Giving every service the same group restores 4.1.0's behaviour exactly. There is deliberately no flag and no top-level default: a group is the only way to express serialization, so there are no precedence rules to reason about.

  As a safety net, epazote now warns at start-up when two services run a byte-identical `cmd`, or invoke the same script with different arguments, without all of them sharing one group — naming the services and suggesting a group. A group covers only the services actually in it, so grouping one side of a shared script and forgetting the other is reported too rather than passing as handled. It is logged at the default verbosity rather than behind `-v`, since packaged installs leave `EPAZOTE_VERBOSE` empty and a diagnostic nobody sees is not a safety net. The systemd unit no longer carries a contradictory `EPAZOTE_VERBOSE=1` fallback that only took effect when its optional environment file was absent or its empty override was removed. The script test looks past a leading wrapper — `sudo`, `env`, a shell or an interpreter — because recovery commands routinely need privileges, and a rule that stopped at the first token would miss `sudo /opt/restart.sh` entirely. It deliberately does not treat a system utility as a shared script whether it is written `systemctl` or `/usr/bin/systemctl`: those services share only the tool, and a warning that fires on services with nothing in common is one operators stop reading — which would cost more than it caught. Where a command is too ambiguous to read — a wrapper carrying its own flags, or a shell construct such as `cd /x && ./restart.sh` — it stays silent rather than guess, since a missed warning costs a scrambled log while a wrong one costs the credibility of every warning after it. It follows that the warning is not a guarantee: a *resource* conflict cannot be seen at all, because nothing in `systemctl restart mariadb` says what else lives on that host. That case is the one this release genuinely leaves to the reader, and it is why this note is explicit rather than incidental. An empty or whitespace-only `group` is rejected at start-up rather than treated as absent, since it can only be a mistake, and group names are matched trimmed so that stray whitespace — invisible in an editor — cannot silently split one group into two. A non-empty `group` without `cmd` is rejected too: groups serialize only commands, while HTTP actions never queue, so accepting the key beside an HTTP-only fallback would make the configuration advertise protection that does not exist.

- **The crate's Rust API is documented as not covered by semver**: `src/lib.rs` exports `pub mod cli` so that the binary and the integration tests share one implementation, and its types mirror the configuration file directly — so every new configuration key becomes a new `pub` field on a `pub` struct. `cli::config::Action` gained `timeout` in 4.0.0 and `group` in this release, and either is a source-breaking change for code constructing it with an exhaustive struct literal. Strictly, that makes every new key a major version. Applying that rule would tie the configuration format's release cadence to a Rust API with no known consumers — the crate has no reverse dependencies on crates.io — so the trade is made the other way round, and is now stated in the crate documentation rather than left to be discovered from a build failure. The stable, semver-covered surface is the command line and the YAML schema: a release will not remove a configuration key, change what one means, or break a working `epazote.yml` outside a major version. Code depending on the Rust types should pin an exact version; `Action` implements `Default`, so building it with `..Default::default()` keeps a later field additive.

### Added

- **Fallback actions are now visible in the metrics**: epazote previously exported the failed check but nothing about the `if_not` actions that followed it. `epazote_fallback_executions_total{service_name, outcome}` counts fallback attempts as `success`, `failure`, or `skipped`: `failure` means at least one action reported failure, `skipped` means a grouped command never got its lock while nothing that did run failed, and `success` means every action that ran reported success and no command was held back. Success on the action's own terms — command exit 0 or HTTP 2xx — is not proof the service was necessarily repaired. A command skipped because its `if_not.group` lock stayed busy is refunded to the `stop` budget when no HTTP action ran. `epazote_fallback_exhausted{service_name}` becomes `1` when that budget is spent and no further fallback actions will run during the outage. `epazote_consecutive_failures{service_name}` publishes the failure streak, including before `threshold` is reached and while a slow fallback is still running. `epazote_fallback_configured{service_name}` distinguishes a service with an available `cmd` or `http` action from one with no fallback. The check timestamp and failure streak are published as soon as the health result is known; only exhaustion waits for fallback completion, because a grouped skip may refund the attempt. These series are seeded for every configured service so zero is represented by a real sample rather than an absent series.

- **`epazote_last_check_timestamp_seconds`**: `epazote_status` is a gauge with no notion of freshness, so a service task that stops ticking keeps publishing its last value indefinitely and a frozen check is indistinguishable from a stable one. The timestamp of the last completed check - recorded whatever the result and before its fallback begins - lets a stuck scheduler be aged out with an ordinary `time() - ...` expression without mistaking a slow recovery action for a health probe that never completed. It is deliberately *not* seeded at start-up: a zero would claim a check had happened at the Unix epoch and immediately trip any staleness alert, so its absence until the first real check is the honest representation.

- **`epazote_build_info{version, revision}`**: there was no way to tell from the metric store which build a host was running, so a partially rolled-out change looked exactly like a fully rolled-out one. The version and git revision are now exported at start-up, always with value `1`, following the usual `*_build_info` convention of carrying the information in the labels.

- **The bundled Grafana dashboard covers the fallback metrics**: *Fallback State* reads `epazote_fallback_exhausted` and `epazote_fallback_configured` together so an armed action, an exhausted budget, and no fallback are distinct states beside *Service Status*. The panel deliberately describes action availability rather than self-healing: an `if_not.http` action may only send an alert or trigger an external workflow. *Consecutive Failures* exposes the streak before `threshold`, *Fallback Executions* splits attempts by outcome, *Time Since Last Check* ages out a task that stopped ticking, and *Build Info* shows the version and revision per node. Each of the ten exported metrics is now referenced by at least one panel.

### Fixed

- **Recovery that is failing is now visible without `-v`**: the log filter defaults to `ERROR` and raises only `epazote::cli::config` to `warn`, so every `warn!` under `cli::actions` was dropped; packaged installs leave `EPAZOTE_VERBOSE` empty unless the operator overrides it. A service that was down, whose `if_not.cmd` exited non-zero on every attempt until its `stop` budget was spent and it was abandoned for the rest of the outage, produced **zero bytes** of log output against the release binary. The metrics recorded all of it, which is what this release added them for, but an operator reading the journal saw a silent process. The three events where recovery demonstrably did not work are now logged at error level: a fallback command that ran and exited non-zero, an `if_not.http` action answered with a non-2xx status, and a service whose `stop` budget is spent and will not be repaired again during this outage. Exhaustion is a state transition, so that last error is emitted once per outage rather than on every later scan; a healthy check resets it. The remaining `warn!` diagnostics are deliberately left where they are: the below-threshold notice fires on every failed check that has not yet reached `threshold`, and promoting it would bury the three lines above in routine bookkeeping.

- **A fallback's own failure is no longer reported as a scan error**: `epazote_failures_total` counts scans that could not be completed — the request could not be made, or the response body could not be read — and a check that answers and merely fails its expectations is deliberately not one. But the result of the `if_not` actions was `?`-propagated out of `scan_service` at all four places that run them, and the scan loop increments the counter on any error it gets back, so whatever the fallback did became the scan's verdict. On the two paths where the check had completed — a command that failed its `expect.status`, or a response that failed its `status` or `body` — the counter moved for a scan that was never in trouble. Against the release binary, two services with no `group` anywhere, both failing an identical check, differed only in whether their `if_not` action could be reached: the one whose webhook refused connections published `epazote_failures_total 4` while its control published `0`. On the other two paths — a request that could not be made, a body that could not be read — the real error was already built and waiting on the next line, but `?` returned before it, so a service whose port was closed was logged only as `fallback command skipped: waited the fallback 'timeout' of 2s …`, naming the recovery instead of the outage and discarding the one line that said why the service was down. The fallback's outcome is already logged where it happens and already counted, by outcome, under `epazote_fallback_executions_total`; it is no longer also allowed to stand in for the scan's result. This predates 4.2.0 — 4.1.0 has the same propagation — but scoping serialization to a group made it routine rather than rare, since a command held back by a busy group is an ordinary, expected condition and was being counted as a service epazote could not reach. `epazote_status`, `epazote_consecutive_failures`, `epazote_last_check_timestamp_seconds` and the `stop` budget are unaffected: all four are written before the fallback runs.

- **Graceful shutdown now reaps active fallback process groups**: fallback commands run in their own process group so a timeout can kill descendants as well as the shell. That same separation let a command survive when Epazote itself received SIGINT or SIGTERM outside systemd: dropping the supervisor process bypassed the timeout path, while the fallback no longer shared the foreground process group. Epazote now handles both signals, cancels and joins every service task, and a cancellation guard kills the complete active fallback group before its leader can be reaped. Packaged systemd deployments already receive equivalent cgroup cleanup; this closes the direct CLI and non-systemd supervisor path. SIGKILL remains intentionally unhandleable.

- **Blank commands and actionless `if_not` blocks are rejected at start-up**: quoted empty or whitespace-only `test` and `if_not.cmd` strings previously reached the shell, where they exit successfully without doing anything. A blank health check could therefore report a service as healthy, while a blank fallback could record successful attempts that repaired nothing. An `if_not` containing only `stop`, `threshold`, `timeout`, or `group` had the same false-positive outcome because no command or HTTP request ran. Commands are now required to contain a non-whitespace character, and every `if_not` must configure at least one of `cmd` or `http`.

- **A `url` that can never be requested is rejected at start-up instead of failing silently on every check**: the configuration checked only that a `url` was *present*, never that it was usable. `url: "not a url"` — or an address written without a scheme, which the URL parser reads as a scheme of its own — therefore loaded cleanly and only failed when the request was *built*, inside the scan and ahead of everything that records or acts on a failure. Against the release binary, with a fallback configured, the service published `epazote_status 0` and `epazote_failures_total 7`, but `epazote_consecutive_failures 0` and every `epazote_fallback_executions_total` outcome at `0`: down permanently, with a streak claiming it had never failed, no `if_not` ever attempted, and nothing in the configuration or the metrics naming the cause. That is the one shape of failure a supervisor must not have, since acting on failure is the entire point — and it silently defeated the two recovery metrics this same release adds. The value is now parsed when the file is read and refused unless it is an `http` or `https` address with a host, naming the key. The scheme is checked for the same reason the rest is: reqwest will build an `ftp://` request and then decline to send it, which fails identically on every check for the rest of the process's life. `if_not.http` is validated the same way — an unusable alert URL is at least visible now that it records `outcome="failure"`, but it still repairs nothing, and one start-up error is better than a series that fails forever. This will refuse a configuration that previously started, which is the intent: such a configuration was never doing the job it described.

- **`epazote_fallback_executions_total` no longer records a failed fallback action as a success**: the `outcome` label was derived from whether the fallback machinery completed, not from what the action reported. A command that exited non-zero and an `if_not.http` endpoint that returned `500` were therefore both counted as `success`. Command exit 0 and HTTP 2xx are successful action results; any other exit or response marks the attempt as `failure` and emits a warning. When no action failed, a grouped command that never got its lock marks the attempt as `skipped`; only an attempt with neither a failure nor a skip is `success`. This measures whether the configured action completed according to its own contract, not whether the service was repaired — an HTTP action may only be an alert. `skipped` records a grouped command that never got its lock when no action that did run failed, whether or not a successful HTTP action ran alongside it: the restart did not happen either way, so the label follows the command. Whether the attempt is refunded to `stop` is separate — it is refunded only when no HTTP action ran — and a skip alongside an action that failed is recorded as `failure`. `epazote_failures_total` remains a count of scan errors, so a failed fallback action does not double-count the service failure.

- **`epazote_consecutive_failures` counts failures for every service, not only those with an `if_not` block**: the streak was incremented inside the routine that decides whether a fallback should run, so only a service that had one configured ever reached it. A service with no `if_not` — a plain check, the simplest and most common thing to configure — published `0` however long it had been failing, while `epazote_status` correctly reported it down. The metric was therefore least reliable for the services whose only failure signal it is, and an alert written on it silently covered a subset of the fleet. Counting is now separated from the decision to act and happens on every failed check, on all four paths that can fail one: a request that could not be made, a response body that could not be read, a status or body that did not match, and a command whose output did not match. Services with an `if_not` block are unaffected — the streak is still incremented before the threshold is compared, so fallbacks fire on exactly the same checks as before.

- **A key written with no value is rejected instead of being read as absent**: YAML spells nothing three ways — `key:`, `key: null` and `key: ~` — and serde maps all of them onto the same `None` that an *omitted* key produces. Throughout the `if_not` block that collapse hid real mistakes. `group:` with nothing after it meant the command ran ungrouped, which is the exact opposite of what writing the key asks for, and precisely the silent behaviour flip the group model was added to eliminate. It was also inconsistent: `group: ""` was already refused as a half-finished edit, while the same edit with the quotes left off was accepted. Worse still was `cmd:`, which produced a fallback that reads in the file as configured recovery and never repairs anything — the most expensive kind of silence in a supervisor, because it is only discovered when a service stays down. `cmd`, `http`, `stop`, `threshold`, `group` and `timeout` now each refuse a value-less key, naming the key in the error so that the message points at the empty line rather than at the block containing it. Omitting a key is unaffected and remains how an optional setting is left unset — including how an ungrouped command is declared. Configurations generated from a template are the likeliest to trip this, and that is the point: an unset variable that rendered as `cmd:` previously disabled recovery quietly, and now stops start-up with the reason.

- **A zero duration is rejected instead of panicking the supervisor at start-up**: `every`, `timeout` and `if_not.timeout` accepted `0s` — the number parsed, the unit was valid, and nothing objected. `every: 0s` then reached `tokio::time::interval`, which panics outright on a zero period, so a plausible typo took down the service task and, with it, the process: `` `period` must be non-zero ``, from inside the runtime, naming no service and no configuration key. The failure arrived at start-up rather than at parse time, which is the worst place for it — past the point where a configuration error is reported cleanly, and phrased in terms of an internal API rather than the file the operator wrote. A zero timeout is no more meaningful: it expires before the request it is meant to bound, so nothing it guards can ever succeed. Zero is now refused where the duration is read, with a message naming the value and the `1s` minimum, so the whole configuration is rejected before any service starts. This also makes the documented rule true: the README has always said the shortest duration epazote takes is `1s`, and until now the parser did not enforce it.

- **An unsupported duration unit is now reported as such, instead of being blamed on the number**: durations were parsed by stripping a single trailing character and reading everything before it as an integer, so `500ms` had its `s` removed and was then parsed as `500m` — which fails, and was reported as `Invalid number in duration: 500ms`. The number was the one part of that value that was correct, so the message sent the reader to inspect the digits while the actual mistake was a unit epazote does not accept. It is now matched whole, and an unrecognised one is named, listed against what is accepted, and told plainly that units below a second are not supported; a value with no unit at all is reported as missing one, which is a different mistake and reads better said directly. A fraction is reported as a third distinct case — `1.5m` is refused for being fractional, with the suggestion to write `90s`, rather than being told the unrelated fact that sub-second units are unsupported. Fractions are refused rather than rounded because reading `1.5m` as one minute or two would be a schedule the operator never wrote. The accepted set is unchanged — whole numbers with a unit of `s`, `m`, `h` or `d` — and the rules are now stated in the README, the example config and the documentation site rather than only discoverable by tripping over them.

- **`epazote_failures_total` now says what it actually counts**: the counter is incremented when a scan returns an *error* — the request could not be made, or the response body could not be read. A service that answers normally and simply fails its expectations is not a scan error: it moves `epazote_status` to `0` and raises `epazote_consecutive_failures`, but never touches this counter. That distinction is deliberate and is locked by tests, but nothing exposed it. The metric's `# HELP` read `Total number of service failures` and the bundled dashboard plotted it under a panel titled *Failures (last 1h)* with no description at all, so both descriptions promised the one thing the counter does not do. Against the release binary, a service returning `500` against `expect.status: 200` published `epazote_status 0` and `epazote_consecutive_failures 5` alongside `epazote_failures_total 0`, while a service whose port was closed published `5` for the same five failed checks — identical outcomes for the operator, opposite readings on the panel named after them. An alert written on `increase(epazote_failures_total[...])` therefore covered connection failures and silently ignored every service that was up enough to answer and wrong enough to matter, which is the more common outage of the two. The counting behaviour is unchanged — altering it would redefine a released metric and fold two different questions back into one series — but the help text now names scan errors and states what happens to an expectation failure instead, and the panel is retitled *Scan Errors (last 1h)* and carries a description saying what it does and does not include. The documentation site already described this correctly; the exported metadata and the dashboard did not, and those are what an operator reads first.

- **`epazote_failures_total` is exported from start-up instead of appearing on the first failure**: the counter is an `IntCounterVec`, and its per-label children are created lazily on first use — which, for this metric, is the increment on a failed scan. A service that had never failed therefore exported no `epazote_failures_total` series at all, not even a zero. That made "healthy, never failed" and "epazote is not running, or the service was renamed or dropped from the config" indistinguishable: both are an absent series that renders as an empty panel, and `increase()` over it returns no data rather than `0`. Since the absent case is the *healthy* one, the metric was missing precisely when everything was working, which is also when an operator is most likely to read the blank panel as broken monitoring. The counter is now published at `0` for every configured service before the first check runs, so the two cases can be told apart and a zero is a real value a dashboard can plot and an alert can compare against. The added cardinality is bounded by the number of configured services — one series each — rather than being open-ended. `epazote_status` is deliberately left lazy: seeding it would have to invent either a `0` (a false DOWN, and a false alert, before the first check has run) or a `1` (a false UP), so it is still set by the first real check. The response-time histogram is left lazy for the reason it already dominates this exporter's series count — twelve buckets plus a sum and a count per service, against one series for the counter.

## 4.1.0 (2026-08-29)

### Fixed

- **Health probes now open a fresh connection on every scan**: each service's `reqwest::Client` is built once and reused across scans, and reqwest's default idle-connection pool kept keep-alive sockets open between scans. When a monitored service closed an idle connection between scans — most easily when a service's `every` interval is close to that server's own idle-connection timeout — the next scan reused a stale socket and failed with a spurious `error sending request for url (...)`, even though the service was perfectly healthy on a new connection. A manual `curl` never reused the socket, so it never reproduced the error, which made the failures look random. Because each such error counts as a failed check, a run of them could reach an `if_not` threshold and fire an unwarranted restart/alert. The probe client now disables connection reuse (`pool_max_idle_per_host(0)`), so every scan connects fresh and the check reflects the service's current reachability. This has been the behaviour since the first Rust implementation, so it is a longstanding latent defect rather than a recent regression.
- **Fallback commands no longer overlap across services**: each service is scanned in its own task with its own failure counter, so when several services failed on the same tick — most easily when a shared dependency goes down, or when a burst of transient errors (such as the stale-connection failures above) trips multiple thresholds at once — their `if_not.cmd` scripts ran concurrently. Independent restart scripts fired at the same instant (a restart storm), and where several services share one fallback script their output interleaved in the shared log. Fallback commands are now serialized process-wide, so only one runs at a time and the rest queue behind it. Only the command takes that lock: `if_not.cmd` and `if_not.http` now run concurrently rather than command-then-HTTP, so an alert is never held up behind another service's restart — which, with the default 300s fallback `timeout`, could otherwise have been minutes. The alert now goes out while its command is still queued, as that command starts, or even when it is ultimately skipped — it no longer depends on the command's fate at all. Waiting for the lock is bounded by the fallback `timeout`, because the caller is the service's scan loop and an unbounded wait would stop probing that service entirely: a command still queued when its wait runs out is **skipped**, logged, and left for the next failed check to retry. `stop` bounds how many times the fallback actions actually *execute*, so an attempt in which nothing ran at all is handed back instead of spent — which is the case when `cmd` is the only action configured and it was skipped. This matters because lock contention only arises during a burst of simultaneous failures — precisely what the lock exists for — so counting skips would let a service exhaust its whole `stop` budget on attempts that never restarted anything, and then be abandoned while still down, having never been restarted once. When an `http` alert is also configured the refund is withheld: the alert takes no lock and was still sent, which is an execution, and refunding it would uncap alerting for exactly as long as the contention lasted. The failed check itself is real and still counts toward `threshold` in both cases. `timeout` is applied to each phase separately — up to `timeout` waiting for a turn, then the full `timeout` to run in — so that a command which does start is never killed part-way through a restart; the trade-off is that one fallback can occupy up to twice `timeout` in the worst case.
- **A failed probe is reported to Prometheus before the fallback runs**: on a transport error or a failed body read, `epazote_status` was only set to `0` after `execute_fallbacks` returned. Since fallback commands are serialized, a scan can sit queued behind another service's restart, so the gauge could keep reporting the last healthy scan for minutes while the service was already known to be down — and the body-read path returned early, so it never set the gauge at all. Both paths now mark the service down first, matching what the command-check and status-mismatch paths already did.
- **Killing a timed-out command's process group is no longer best-effort**: 4.0.0 started running each command in its own process group so a timeout could take its descendants with it, but the result of the `killpg` call was discarded. A kill the kernel refuses leaves those descendants running for as long as epazote does — the exact leak the process group exists to prevent, repeating on every scan — and swallowing the result left nothing in the log to explain a host slowly filling with orphaned restart scripts. The result is now checked: the group already having exited counts as success, and anything else is logged as an error naming the group. Exactly how much a refusal says about *which* members survived differs between Linux and the BSDs, so it is reported rather than interpreted. A group id of `0` is also refused outright, since `killpg(0, ...)` would signal epazote's own process group.

### Release

- **Smaller release binary**: the release profile now uses thin LTO, a single codegen unit and symbol stripping, cutting the binary by roughly a third (~14.3 MiB to ~9.8 MiB on `aarch64-apple-darwin`) with no behaviour change. `panic` stays the default `unwind`, and the build now refuses `panic = "abort"` outright rather than trusting the profile to stay that way: aborting would stop `Drop` cleanup — including the `kill_on_drop` that reaps a timed-out fallback child — and would also let a single panicking service task kill the whole supervisor, ending monitoring for every other service, instead of being contained and reported. Since tests never build with the release profile, that setting is the one part of this change no test could have caught.

## 4.0.1 (2026-08-28)

### Release

- **aarch64 release artifacts**: releases now also build `aarch64-unknown-linux-musl` (on a native ARM runner) and `aarch64-apple-darwin`, so each release ships eight artifacts instead of four — tarballs, RPM and DEB for both architectures. One architecture failing no longer cancels the others, so a partial build cannot silently produce a partial release. The test matrix gained `ubuntu-24.04-arm` to match, since Linux is the primary target.
- **Dependency refresh**: `chacha20`, `cpufeatures`, `flate2` and `miniz_oxide` were updated to their current releases. No behaviour or API change.

## 4.0.0 (2026-08-27)

### Breaking changes

- **`test` commands can now be killed**: command checks are bounded by the service `timeout` (default **5s**). A command that never returned previously blocked that service's task forever, silently stopping every later scan. A command that exceeds the timeout is now killed and counts as a failed check, so the normal `if_not` threshold/stop path runs. **A health-check script that legitimately runs longer than 5s must now set `timeout` explicitly**, e.g. `timeout: 30s`.

### Added

- **`if_not.timeout`**: recovery actions get their own time budget, default **300s**, since a restart legitimately takes far longer than a health probe. Applies to both `cmd` and `http`. Set per fallback, e.g. `if_not: { cmd: "systemctl restart app", timeout: 15m }`. Note that a hung recovery still holds that service for the full budget, so lower it when recovery should never linger. Accepts `s`/`m`/`h`/`d` like every other duration, and the unit is required.
- **Fallback command output**: stderr from a command is now logged instead of captured and discarded, making a failing recovery diagnosable. It is logged at warning level only when the command fails, since healthy commands legitimately write to stderr, and retention is capped while the pipe is still drained so a chatty command cannot grow memory or block.
- **Command services now emit metrics**: `test` services previously recorded no metrics at all — not `epazote_status`, not `epazote_response_time_seconds` — so a failing command service was invisible to Prometheus and only appeared if its fallback errored. Both are now reported per check. Existing dashboard panels will start showing command services that were previously absent. `epazote_failures_total` is unchanged and still counts scan errors only, matching the HTTP path.

### Fixed

- **`if_not` now runs for unreachable HTTPS services**: a failed SSL certificate check no longer aborts the scan before the HTTP request is made. Previously the check was error-propagated, so an unreachable `https://` service returned early, was counted in `epazote_failures_total` with `epazote_status` `0`, and its configured `if_not` fallback never ran — exactly when remediation is needed. The scan now continues to the HTTP request, so the outcome flows through the normal `expect`/`if_not` path instead. **If you alert on `epazote_failures_total` for HTTPS services, expect fewer counter increments and fallbacks that now actually fire.** Certificate failures are logged as a warning. Note that a service whose recovery has silently never run will now start executing it.
- **The certificate check is now bounded too**: neither the TCP connect nor the TLS handshake had a timeout, so a blackholed address or a peer that accepts TCP and never completes the handshake stalled every later scan for that service, even after the check stopped aborting the scan. It is now bounded by the service `timeout`.
- **A command that could not run is never reported healthy**: execution failures (a spawn error, or a command killed at its `timeout`) were reported as exit code 1. A hung command configured with `expect.status: 1` therefore matched, and was reported healthy with no fallback — the worst possible outcome for a service that was not being checked at all. Execution errors are now distinct from a genuine exit status: they always fail the check, `EPAZOTE_ACTUAL_STATUS` is unset for them, and `EPAZOTE_ERROR` is `command_error` rather than `command_failed`.
- **`if_not.http` is time-bounded**: the shared fallback HTTP client had no timeout, so an alert endpoint that accepted the connection and never answered hung the request and stalled every later scan. Both fallback actions are now bounded by `if_not.timeout`.
- **Failed certificate checks back off**: only successful checks were cached, so a service that was down repeated the whole connect and handshake on every scan ahead of the HTTP request. A failed check is now remembered for 60s before being retried, and is stamped when it finishes rather than when it starts — a check that burned its whole `timeout` was otherwise cached already expired, defeating the backoff for exactly the slow failures it exists for. Successful checks are stamped the same way, so the exported expiry is no longer short by the duration of the check.
- **Failed fallback HTTP bodies are logged**: the response body was consumed with its result discarded, so a fallback whose headers arrived and whose body then failed or timed out was reported as a clean success.
- **Timed-out commands no longer leak descendants**: killing the spawned shell left any processes it had started running, so a timeout leaked them on every scan. The command now runs in its own process group, which is signalled as a whole. Its error also names the setting that supplied the budget: service `timeout` for a `test` health check, and `if_not.timeout` for a fallback command, rather than sending both users to the service setting.
- **`if_not.cmd` and `if_not.http` are genuinely independent**: a failing or timed-out fallback command no longer skips the configured HTTP action, which is often the only way an operator learns that recovery failed. Both run, and the first error is still reported.

### Performance

- `expect.body`/`expect.body_not` patterns are compiled once and cached instead of recompiled on every response. Compilation costs orders of magnitude more than the match itself (~268us to compile a complex pattern versus ~6us to run it over a 64KB body).
- The system root certificate store is no longer cloned on every HTTPS scan. It was passed by value, so all ~150 system roots were copied even on the scans that hit the 12h certificate cache and open no TLS connection.
- The HTTP method is mapped to a constant instead of being formatted to a `String` and re-parsed on every request, and the response buffer is sized from `Content-Length` (bounded by `max_bytes`) instead of growing chunk by chunk.

### Security

- Refreshed dependencies, including `h2` 0.4.15 -> 0.4.19, which clears RUSTSEC-2026-0258 (unbounded empty DATA frames). A daily `cargo audit` workflow now runs in CI, and the repository has a published security policy.

## 3.7.0 (2026-06-10)
- **Full-Body Scanning (#20)**: `expect.body` and `expect.body_not` now scan the entire response body using a sliding window instead of only checking the first `max_bytes`. `max_bytes` now bounds memory only — it no longer truncates the search — so expected text deep inside a multi-MB body (e.g. `pg_up` in a 5MB `/metrics` page) is found. Reading stops early once every configured matcher has found its text, and the scan is time-bounded by the service `timeout` (default 5s): a body that takes longer to read is aborted and reported as `service 'timeout' exceeded while reading the response body`. Note: matches longer than half the window may be missed if they span a window boundary, so keep `max_bytes` comfortably larger than the longest expected match.
- **Lower Default Memory Footprint**: when `max_bytes` is unset, defaults are now matcher-aware: `body`/`body_not` scans use a 64KB sliding window (down from buffering 512KB) so monitoring many services from one host stays lightweight, while `expect.json` keeps buffering up to 512KB since a JSON document must be parsed whole. Setting `max_bytes` explicitly overrides the JSON buffer and non-JSON scan window; when `body_not` is combined with `expect.json`, the scan window is capped at 64KB and never larger than `max_bytes` (so `max_bytes: 0` still means "don't read the body"), while JSON buffering follows `max_bytes`.
- **Anchored Regex Correctness**: `^`/`$` (and `\A`/`\z`) in raw `r"..."` patterns refer to the start/end of the whole response body, not of each scan window. Anchor detection now uses exact regex parsing (`regex-syntax` HIR), so shapes like `(?i)^foo` or `(foo$)` are treated as anchored, while `^foo|bar` and `(?m)foo$` are correctly evaluated on every window. Known approximation: in mixed anchored/unanchored alternations the anchored branch may still match at a window edge, and `(?m)` line anchors are approximated near window boundaries.
- **Fallback on Body-Read Failures**: a body read that fails or times out mid-stream now runs the normal `if_not` threshold/stop fallback path with `EPAZOTE_ERROR=body_read_error` before the error is reported, instead of silently skipping remediation.
- **`body_not` + `json` Full Coverage**: when `body_not` is combined with `expect.json`, the forbidden pattern is now scanned over the entire body in a single streaming pass (the JSON document is still parsed from the buffered prefix), instead of only checking the buffered bytes.
- **Clear Failure Reasons (#20)**: when a check fails, logs now state why — e.g. `reason: body_mismatch: expected body 'pg_up' not found in 5765639 bytes scanned` — in both pretty and JSON log formats, instead of only `matches: false`. JSON-body checks report when the body was truncated by `max_bytes`.
- **Strict Config Validation (#20)**: unknown keys in `epazote.yml` now fail at startup with a clear error instead of being silently ignored (e.g. `max_size` reports `unknown field 'max_size', expected one of ... 'max_bytes' ...`). Invalid or empty `body`/`body_not` regex patterns are also rejected at startup (e.g. `invalid regex in 'expect.body': r"(unclosed"`) instead of failing every check at runtime. Review your config for stray keys before upgrading.
- **Verbosity Errors (#19)**: invalid `EPAZOTE_VERBOSE` values now produce a helpful error (`expected a number, e.g. EPAZOTE_VERBOSE=2 equals -vv`) instead of `invalid digit found in string`. Numeric values map as before: 1=info, 2=debug, 3+=trace.
